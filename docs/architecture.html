Architecture

How WishUnify is built

A config-driven pipeline loads each client's sources into a layered warehouse (Bronze → Silver → Gold). A web app reads the finished Gold tables for dashboards and AI questions. Everything client-specific is configuration, not code.

Big picture

The data layers

All data lives in a single DuckDB database file (data/warehouse.duckdb by default), organised in four schemas. DuckDB is an embedded analytical SQL database, a fast columnar engine inside one file with no separate database server to run.

Every row in every layer carries a tenant_id, so many clients can share one installation while their data stays separate.

One refresh, step by step

A refresh runs from the Run now button, the scheduler, or python -m cdp run.

  1. Validate configurationEvery client file and mapping is checked; all problems are listed at once and the run stops before touching data.
  2. Start a working copyThe live warehouse is copied to warehouse.building.duckdb. The app keeps serving the live copy during the whole run.
  3. Bronze: extract each sourceEach source's connector reads its data. A failing source is logged and skipped; its previous data stays in use. A full load returning 0 rows does not wipe the old data.
  4. Silver: map to the standard modelSQL is generated from each mapping file and every source is unioned into std_* tables, with normalized email, phone and an identity key.
  5. Silver: resolve identitiesRecords sharing an id, email or phone are grouped into one customer id.
  6. Silver: business tablesGolden customer record, transactions, lines, tickets, sessions (sql/silver).
  7. Gold: calculationsCustomer 360, RFM, segments, tiers, churn risk, cohorts, funnel, products, revenue (sql/gold), using each client's business rules.
  8. Quality checks and history8 data-quality checks per client; results, per-source status and run status are written to Meta.
  9. PublishThe working copy atomically replaces the live warehouse. The app notices the new file and shows the new data. If the run failed, the working copy is discarded and live data is untouched.

Run status is success, partial (some sources failed; CLI exit code 2) or failed (exit code 1).

Identity resolution

Each person-related row gets an identity key:

  • a customer record: <namespace>:<id>, e.g. shopify:5001
  • a row that points at a customer id (e.g. an order's customer id): the same shopify:5001
  • a row with only contact details: email:riya.sharma@gmail.com or phone:9876543210

Keys become nodes in a graph; nodes sharing a normalized email (lower-cased, trimmed) or normalized phone (digits only, last N digits, N set per client) are joined, and each connected group becomes one customer with a stable customer_id. The match reason (email, phone, multiple emails, single source) is stored so users can see why records were merged.

Golden record: when sources disagree (e.g. two names), each attribute is taken from the highest-priority source that has it (priority is set per source), then the oldest record.

Customer 360 calculations

Lifetime revenue, orders, AOVFrom completed orders across all sales sources. Refunded and cancelled orders are counted separately and excluded from revenue.
RecencyDays between the last completed order and the as-of date.
RFM scores (1–5)Buyers of the client are split into five equal groups by recency, frequency (orders) and monetary value (revenue); 5 is best.

Churn riskHigh / Medium / Low from days since last order versus the client's thresholds and the customer's own usual gap between orders.

Configuration model

Three kinds of configuration, all editable from the admin screens or as JSON files:

Platform

config/platform.json: branding, warehouse location, as-of date, default business rules.

Client (tenant)

config/tenants/<id>.json: name, currency, phone digits, rule overrides, and the list of sources with their connectors.

Mapping (source type)

config/source_types/<name>.json: how one kind of system's columns become standard columns. Reusable across clients.

Secrets are never stored in these files; they are referenced by name and resolved from the encrypted credential store or environment variables.

Reliability features

  • Zero-downtime refresh: builds in a copy, swaps in when done; the app never reads a half-built warehouse.
  • Failure isolation: one bad source doesn't stop the others; its last good data stays in use.
  • Empty-extract protection: a full load returning 0 rows keeps the previous data (status "warning").
  • Incremental loads: per-source watermark; only new or changed rows are fetched; de-duplicated by key, latest version wins.
  • Validation before every run and every admin save.
  • Run history and per-source errors in Meta and on the Data pipeline page; JSON logs in data/logs/pipeline.log.
  • Data-quality checks: orders linked to a customer, valid order status, orders have a value, customers with email, unique order ids, lines with a known product, tickets linked to a customer, no future order dates.
  • Exit codes for automation: 0 success, 2 partial, 1 failed.

Scale and extension

  • Volume: one DuckDB file on one server comfortably handles tens of millions of rows. Plan disk for about 3× the warehouse size, because a refresh builds a full copy before swapping.
  • Bigger clients: the Silver and Gold logic is plain SQL and the standard model is engine-neutral, so it can be moved to Databricks, Snowflake or Microsoft Fabric for very large data.
  • New systems: add a mapping (UI or JSON). New connector kinds are added in cdp/connectors.py.
  • New industries: add entities to cdp/model.py and the SQL that uses them (e.g. subscriptions, policies, accounts).
  • New KPIs or pages: add a SQL file to sql/gold and a page in app/views.
